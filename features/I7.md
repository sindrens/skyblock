# Resource pack v2 + font · id: I7 · status: Locked · version: 4

Cluster GUI-V3 (GUI look v3, 1 Nov 2026), with I9 v3 (standard and FORMAT), `docs/FORMAT.md`, G9, G7, G8. v3 was **Locked** on 31 Oct (ledger `I7-R1-01` to `I7-R1-07`, build specs `GUI-P1-PACK.md` and the built pack module on branch `q/gui-phase1`); a verbatim copy is in `feature-overview/rounds/I7/v3-locked.md`. **v4 is Locked on 1 Nov 2026: the owner answered V3-Q1 b ("full MC Hub, a little different"), which reverses the locked "no fonts, no glyphs, no negative-space titles" rule in the minimal scope of section 10 and 11 (ledger `I7-R2-01`, scope note `I9-R2-09`); icon look `I9-R2-03`, plain star `I9-R2-04`, logo `G7-R2-01`, Depths highlight `G9-R2-01`.** Build specs: `GUI-ICONS-FINAL.md` (icons), `GUI-FONT.md` (font and frame layer).

## In one sentence
Pack v1 is deleted at once and the server runs on pure vanilla; later a small **pack v2** (our own simple icons repainted on real vanilla base items, plus at most one optional chest background) is **forced for Java players** and asked for after they have joined, so Bedrock and anyone without the pack still see the same menus on the normal items. **v4 (decided):** the same pack also carries one small **font** that gives Java players a panel with a plaque and cartoon title lettering, a soft tile behind each item (empty slots are not drawn) and a logo on the scoreboard and tab; Bedrock, no-pack and fail-open viewers keep the plain vanilla chest and plain titles (sections 10 to 14).

### 2. What pack v2 contains (small on purpose)
- **Item icons only.** One 16 x 16 (or 32 x 32) PNG per icon, a model file per icon, and one `assets/minecraft/items/<base item>.json` per base item that selects the model by the `custom_model_data` string and falls back to the normal vanilla model.
- **Our own new icons (owner GUI-Q9):** the v1 art is discarded. Every icon looks like a vanilla Minecraft item, simple, easy to understand and readable at a glance by every kind of player; the base item stays the same, only the look is ours.
- **Planning size of the first full release: 50 icons, under 100 KB** (v1 was 212 KB with fonts, 3D models and sounds).

| Shop tabs | 9 | one per tab (C5) |
- **Later, optional (phase 3):** 7 crate keys (base item tripwire hook), tool tier and skin icons once E10 locks its list, mastery tree node icons once B14 locks its layout. Skins are a Java bonus: Bedrock sees the base item, so nothing paid may depend on being seen through the pack (developer decision below).
- **Nothing else in the pack:** no shaders, no sounds, no language files, no armour or HUD changes. **v3 said also no fonts, no glyphs and no per-menu backgrounds; v4 (decided, V3-Q1 b) allows exactly two fonts and the assets of section 11, nothing more.**
- **Rule for each icon:** the vanilla base item and the item name explain it alone (I9 section 7). The pack only makes it ours.
- Technical note (checked against the code): the pack icon is a `custom_model_data` string on the real base item, sent only to viewers whose status is LOADED. It is **not** `item_model` (a client without the pack would draw the purple-and-black missing model). `item_model` is allowed only toward another vanilla model (the gold tier tool uses `minecraft:golden_pickaxe` today).

### 3. The one optional container background (phase 2, only if the owner wants it after seeing phase 1)
- One replaced texture: `assets/minecraft/textures/gui/container/generic_54.png`. Every chest-sized screen draws from it: all our menus, real chests, ender chests and barrels, for any number of rows, **including the player-inventory half**. It cannot differ per menu, per row count or per player group; empty slots are still drawn as slot cells.
- So it can only be a **global tint and frame**: same slot grid, no text, no logo, light enough for the dark-gray vanilla title and for item names to stay readable.
- Decided: icons first, background later (GUI-Q1, owner). Phase 2 is a separate owner decision with the icons already seen on a real screen.
- **v4 note:** the per-menu panel of the frame layer (section 10) is NOT this global texture. It is drawn by the title font on top of the vanilla window, so real chests, ender chests and barrels are untouched. The global `generic_54.png` skin stays an optional extra only for making real chests match (phase 2e).

### 4. Forced for Java, asked after joining (GUI-Q2, owner)
- **The pack is forced for Java players** ("yes and will ask when the player has joined the server"). The prompt is sent **after the player has joined**, not before joining and not in the configuration phase. This changes the old detail "asked before joining" (answer 77, OWNER_PRINCIPLES 7); "forced" stays (answers 33 and 77).
- **Declining, or a failed download, kicks the player** with a friendly message that says why the pack is needed (it only repaints the icons, about 100 KB) and exactly how to try again (turn on Server Resource Packs for this server, then rejoin). The kick is never silent and never staff-alerted as an incident.
- **Bedrock cannot be forced:** Bedrock (Floodgate) players are never sent the pack and play without icons on the normal items.
- **Join order (default, owner may veto):** the player joins the spawn world, the pack prompt shows at once, and the join flow of A1 (welcome, tutorial start) begins when the answer is LOADED, or after 15 s if the client never answers. Player data is saved before a kick, so a tutorial in progress resumes after the retry.
- **Fail-open safety (developer decision):** if the pack host itself is unhealthy (a self-check every 60 s cannot fetch its own file, or the file is missing), the server stops requiring the pack until it is healthy again and alerts staff once. A broken host can therefore never lock everyone out.
- **Switch:** `pack.required` (default true) in the phase 1 module config; set false and reload to make it an optional offer without a kick. Nothing is sent and nobody is kicked before phase 1 exists (phase 0 is pure vanilla).
- Because everything works on the base items, a player who somehow has no pack (Bedrock, staff test, fail-open) sees the same menus.

### 5. Hosting and reload (phase 1, fresh module)
- A new small `modules/pack` (config `pack.yml`: `enabled`, `required`, `url`, `host.port`, `host.public-host`, `prompt`, `timeout-seconds`). It serves one zip bundled in the plugin jar with its SHA-1 from a tiny built-in web server (design of v1's `PackHost`, no CDN, no DNS record), or from an external `url:` set in config.
- Sender: after `PlayerJoinEvent` (Paper `Player#sendResourcePacks` with `required` true and the prompt); statuses LOADED, DECLINED, FAILED, BEDROCK, PENDING tracked in memory only; `PackService.hasPack(viewer)` is the one gate for icon rendering.
- The pack id never changes; the version (SHA-1) does, so clients download only after a real change. Online players get a changed pack on `/pack reload` with a one-line notice.
- Pack format: `pack.mcmeta` supports 1.21.5 to the current client (the format range is looked up in phase 1; icon files use only base items that exist in 1.21.5, C1-R2-24).

### 6. Bedrock
- Bedrock players are never sent the Java pack (Floodgate check). They see chest menus with the **vanilla base items** and our coloured names.
- Custom icons on Bedrock would need Geyser custom-item mappings plus a Bedrock pack. That is not planned; if the owner later wants it, it is a separate phase after launch. Every icon must therefore be readable by its base item and name (I9 section 7).
- The owner or one tester checks each pack release on a Bedrock phone (decided 78): joins, menus on base items, no prompt.

### 7. Fallback ladder
Pack loaded (Java) -> our icon on the base item, and (v4) the frame layer: panel, plaque, soft tiles, lettering, logo. Bedrock, `pack.required` off and declined, still downloading, fail-open, pack module off, the `/settings` switch "Plain menus" -> the base item itself and the plain vanilla title. Same menu, same slots, same text. `PackService.hasPack` stays the single gate; `Glyphs.of(viewer)` is the single gate for every glyph.

### 8. Who draws what
- **Owner:** draws every PNG himself (original art only; no copied or traced Mojang textures), at 16 x 16 or 32 x 32 on a transparent background, in the "custom looking vanilla" style: simple shapes, strong silhouettes, readable at a glance.
- **Developer:** icon ids, model and `items/*.json` files, the build and zip, SHA-1, hosting, tests, the vanilla fallback in code, and an `icons.yml` list (id, base item, where used) that tells the owner exactly what is missing. A contact sheet of all base items (the plain look) is produced so the owner draws against the real background.
- **v4 note (1 Nov):** the icon pictures come from the parallel icon design the owner approves (this card only fixes the keys, slots and base items); the frame sprites of section 12 are generator placeholders until the owner or that design replaces them by file name. No pixel art is drawn in this review.

### 10. Font feasibility verdict (checked 1 Nov 2026) and the frame layer (v4, decided)
**Verdict: feasible on Java 26.3 for panels, plaque lettering and logo; impossible on Bedrock (plain fallback); the owner accepted a plain look for Bedrock and no-pack players (V3-Q1 b, V3-Q5 a). The render order of title glyphs over slot items on 26.3 is still unverified: phase 2a is a go / no-go spike.**

What was checked (sources: Minecraft Wiki "Font" and "Font definition" pages, the Java 26.1, 26.2 and 26.3 release notes, the pack v1 code at tag `pack-v1-final`):
| Question | Answer |
|---|---|
| Does the 26.3 client still support custom fonts? | Yes. Font providers `bitmap`, `space`, `ttf`, `unihex`, `reference` and the `font` key on every text component are unchanged since 1.20; the 26.1 to 26.3 notes list only font bug fixes (TTF glyphs on glow signs, Unicode gaps, a font-settings cache bug fixed in 26.3). Resource pack version of 26.3 is 97.1, inside our 55 to 97 range |
| Negative-space panel backgrounds | Yes: a `space` provider with negative advances moves the cursor back, a tall bitmap glyph (height up to the full window, `ascent` at most its height) draws a whole-window background from the title, `shadow_color` none removes the glyph shadow (all 1.21.5+ clients). This is what v1 did (31 backgrounds) |
| `minecraft:default` override vs a named font | Use a **named** font (`phoenix:frame`, `phoenix:title`) inside the title component. Overriding `minecraft:default` would change every text on the screen, including lore and other servers' text, and cannot be limited per viewer |
| Bitmap vs ttf lettering | Bitmap (pixel art, crisp at every GUI scale, drawn or generated). A ttf provider (a licensed open font, antialiased) also works; the generator can switch, the plaque widths come from a metrics file either way |
| Shaders needed? | No. Not for panels, plaque, lettering or logo |
| Is the lettering readable by a narrator? | Yes if the lettering font maps normal ASCII letters to the cartoon glyphs: the title string is real words. Only panel, tile and logo glyphs are private-use code points |
| Draw order of the title over the slot items on 26.3 | **Not verified by a human.** The label is drawn after the container texture, and items are drawn above it in the classic renderer (that is why glyph backgrounds work); the GUI renderer was reworked in 1.21.6, so phase 2a must check it on a real 26.3 client first. If items drew under the panel, the frame layer is dropped and nothing is lost (plain fallback) |
| The panel cannot be narrower than a chest | True: the vanilla window texture is always drawn under the glyph. Only space **above** the window is free, so the plaque extends 8 px above it (a pack constant, see section 11). Making the window itself non-rectangular needs a replaced `generic_54.png`, which also changes every real chest (rejected) |

Where the font can and cannot be used (Java 26.3; every row is per viewer):
| Surface | Works | Used in v4 | Why |
|---|---|---|---|
| Chest and inventory title | yes | **yes**: panel, plaque, tiles, lettering | the whole point |
| Scoreboard title | yes (title is a component since 1.20.3); a taller glyph overflows the title row upward and widens the board | **yes**: logo only (V3-Q18) | per-player boards already exist |
| Scoreboard lines | yes | no | readability, width |
| Tab header and footer | yes (pad blank lines to the glyph height) | **yes**: logo only (V3-Q18) | Bedrock has no tab header |
| Boss bar name | yes (the bar sprite itself is unchanged) | no | plain text is clearer |
| Holograms (text displays) | yes, but one entity is seen by everyone, so a no-pack or Bedrock viewer would see boxes | no | cannot be per viewer |
| Chat, action bar, titles | yes | no | readability, Bedrock, copy-paste |
| Item names and lore | yes | no | readability |

**Bedrock and Geyser (to the best of current knowledge; the owner's Bedrock phone check of decision 78 verifies it each release):** Geyser flattens a Java text component to a string and **drops the `font` key**; private-use code points reach Bedrock, which draws its own emoji for `U+E0xx` and `U+E1xx` and blanks for others. So a glyph title would show as odd spaces. Rule: Bedrock never receives a glyph (`Glyphs.of(viewer)` is empty for Floodgate players), gets the plain title and the vanilla chest, and loses nothing functional. Nothing can make the frame layer appear on Bedrock without a separate Bedrock pack and Geyser mappings (not planned, as v3).

**Risks and answers:**
| Risk | Answer |
|---|---|
| Title text length limits | The title component is one font run of about 200 characters plus the lettering: far inside the protocol limit. Bedrock's 32-character rule does not apply (plain title). The plaque holds at most 16 letters (test) |
| Plaque clipped on a small window | Plaque extension 8 px (pack constant `plaque_extend`, baked into the glyph ascent, not a server setting); at GUI scale 3 on a 720p window the margin above a 6-row window is 9 px, so the spike checks scales 1 to 4 and the value is tuned there |
| Accessibility | Lettering = ASCII code points (narrator reads words); strong dark outline; a `/settings` switch "Plain menus" (developer decision); information is never only in the frame |
| ViaVersion and old clients | The pack range starts at 1.21.5; `shadow_color` needs 1.21.4+; older clients cannot join anyway (C1-R2-24) |
| Translations | Titles are server strings in English (principle 6); client language packs do not change them |
| Font file size and GPU memory | About 30 KB of PNGs; a handful of textures; no per-tick cost |
| Pack not loaded yet, reloaded, hash changed, declined | Gate = status LOADED; surfaces refresh on `PackStatusEvent`; a menu opened before LOADED is plain; fail-open and decline fall back to plain |
| Mojang changes GUI rendering again | The frame layer is isolated behind `Glyphs` and config switches (`gui.font.enabled/panels/titles/tiles/logo`, editable in `/admin`); every game drop gets a 15-minute check (I8) |
| Glyph advance and ascent off by a pixel | Pure goldens in tests, tuned once in the spike (v1 used ascent 13 and offset +8 as a start) |
| Players typing glyphs to spoof | `PrivateUse.strip` on all player text stays |

### 12. Generation approach (the owner overwrites by name)
- `tools/build_panels.py` (stdlib only, same style as `build_icons.py`): `art` writes the **sprites** that are missing (a 24 x 24 9-slice panel frame with 8 px corners, plaque left cap, middle and right cap, the soft tile, the logo, the lettering sheet) as placeholders in our palette; `pack` composes the final glyph PNGs from the sprites (panels by 9-slice for the three window sizes, plaques from the caps at three widths, the cell glyph rows), writes the font JSON and `frame-metrics.json`; `sheet` writes a preview of one panel with plaque, tiles and lettering at 3x on a game-like background; `check` fails when the committed tree differs.
- **The generator never overwrites an existing PNG** (as `build_icons.py`): the owner replaces a **sprite** (for example `panel_frame.png`, one small file) and every panel, plaque and glyph is rebuilt from it, or replaces a **final** glyph by name for full control.
- Placeholder style: flat parchment-grey panel, dark red `#D1202F` frame (the red identity), flame gold lettering with a dark outline, ember-orange tile edge; the owner repaints to taste.
- One panel colour for every menu (V3-Q9 default); a tint per area would only add more sprites.

## What the player sees
- Phase 0: nothing about a pack at all. No download prompt, no kick, no text screens. Plain coloured `[Name]` ranks and normal Minecraft items in menus.
- From phase 1 (Java): a short "Phoenix Skyblock icons" prompt right after joining, then the same menus with our own icons. From phase 2 (v4, if V3-Q1 is yes): the panel with a plaque, soft tiles behind items and the logo on the scoreboard and tab. Decline and you are kicked with a friendly line and how to retry. Bedrock: the normal items, no prompt.

## Rules and limits
- Never send what a client cannot draw: a model string goes only to LOADED viewers. No pack model reaches Bedrock.
- Size targets: Java zip 100 KB (hard 1 MB); downloads in under 1 s.
- Original art only. The pack id never changes; the version number does.
- Performance: the pack is sent once at join; `hasPack` is a map lookup; no per-tick work.
- A pack kick is not an incident: no staff alert; `/pack status` counts statuses. A fail-open switch-off alerts staff once.
- **v4 font rules (decided):** a custom glyph reaches only viewers with the pack LOADED who are not on Bedrock (`Glyphs.of(viewer)`); tooltips, lore, chat, messages, holograms, boss bar text, action bar and scoreboard lines never use the font; private-use code points start at U+E300 (never U+E0xx or U+E1xx, which Bedrock draws as its own emoji); `PrivateUse.strip` stays on all player text.
- Size: Java zip target 200 KB, hard limit 1 MB (today: 95 KB with 75 placeholder icons; the frame layer adds about 30 KB).

## Developer decisions (defaults; the owner only vetoes)
- **Phase 0 is its own build** (`GUI-PHASE0.md`): remove v1, no menu redesign, no new pack code. Rollback is `git revert`; the old jar and tag `pack-v1-final` keep v1 reachable.

One source, editable in `/admin`.
- **Rank display without the pack:** `BadgeService` no longer means "pack present": it always renders the simple `[Name]` form (Bedrock legacy-code form for Bedrock viewers, text gradient for gradient ranks). The font form, pack flags and `BadgeOptions` pack, reduced-motion and large fields are deleted. `/rank preview` keeps the simple, Java and Bedrock lines (staff tool for F2's colour choices).
- **Settings migration:** the three retired switches stop being registered; stored values are ignored (same pattern as `RetiredTexts`); no database change (the pack has no tables). `rank-color` and `skyblock.chat.rankcolor` stay.
- **Near-duplicate colours stay in phase 0:** hatchling `#FF9A4D` and builder `#FF9A3D` look almost the same. Phase 0 keeps every value identical; F2 and G8 fix the distinct-colour rule when the seven rank names are decided.
- **Phase 1 build:** `icons.yml` (id, base item, screen) checked by a unit test: every icon id used in code has a base item and a PNG, no PNG is unused, every base item exists in 1.21.5. A Gradle task zips `resourcepack/java` into the plugin resources and writes the SHA-1. The forced flow, fail-open check and kick texts have unit tests for the pure parts (status mapping, kick or not, timeout).
- **Paid cosmetics:** nothing sold for credits may be visible only through the pack. Tool skins, trails and sets must show something for everyone (name colour, lore, glint, dyed leather colour, particle); the pack look is a Java bonus and the shop page says "Java with the pack" (ripple E10, E13, I10).
